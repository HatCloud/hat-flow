# Meta-Skill Philosophy（spec-skill 参考）

> 跨技能设计哲学——`spec-skill` / `spec-task-skill` / `skill-create` / `skill-revise` / `skill-test` 这 5 个"元技能"（管理技能创建/修改/测试的技能）共同遵守的原则。供改动这 5 个技能时先读，类似 canonical 母本之于自进化流程的定位，但这份是"为什么这样设计"的解释性文档，不是运行时必读的操作流程，不做 `!cat` 强注入。

## 背景

2026-07 一轮诊断发现：这 5 个技能最大的问题不是规则内容不对，而是**规范权威自身没有被规范权威约束**——`spec-skill` 作为唯一标尺，正文体量超出自定预算十倍以上，且存在正文内部自相矛盾、正文与 README.md 不同步；而 `skill-create`/`skill-revise`/`spec-task-skill` 全部无校验地信任这份有问题的权威源（`!cat` 全文预注入），意味着权威源的腐化会无声扩散到全部下游。以下原则是这轮诊断+改造沉淀下来的设计立场，供后续维护者判断"这个改动是否符合本体系的哲学"而不必每次重新推导。

## 原则

1. **高频加载权威源必须是自己体量预算的第一个遵守者，且预算要靠机制不靠自觉。** `spec-skill/SKILL.md` 被 `spec-task-skill`/`skill-revise` 每次全文 `!cat` 预注入，是真实发生的高频加载路径；它自己越预算，下游每次注入都在为超标买单。`bin/hat-skill-lint` 就是把这条原则变成可执行检查的手段。

2. **厚流程本身不是问题，"厚而不可自证"才是问题。** 这 5 个技能的多阶段流程、对比实验测试门、两段式自进化，是多轮实战沉淀的护栏，不该为了"看起来精简"而整体推倒重来。真正要清零的是自相矛盾（同一份文件里两处说法打架）和体量膨胀，而不是规则数量本身——新增机制前先问"这是在补一个真实验证过的缺口，还是在为厚而厚"。

3. **"写入闸"这类跨版本演化的规则，全仓只能有一种当前语义，不能新旧并存。** 自进化写入闸曾从"论证式"（写前论证为何不能上移）改为"反转式"（默认写入、无需论证），但改造只触及了部分文件，导致 SKILL.md 正文、SKILL.md 自己的 Checklist、README.md 三处出现新旧混杂。规则改版时要一次性扫描所有复述该规则的地方，不能只改"当前正在编辑的那一处"。

4. **README.md 不承担"翻译/镜像 SKILL.md"的职责。** 这是技能曾以英文写作、README 作中文对照译文时代的遗留定位；现在正文已统一陈述式中文，翻译职责已无意义，且"覆盖目的/触发条件/核心流程/关键规则"的旧范围本身是持续复述、注定漏同步的结构性诱因。现行定位：README 只做①3-5 句摘要 ②SKILL.md 放不下的补充信息，不复述 Iron Laws/Process。

5. **description 采用"what + when"并重，不采纳更激进的"只写 when"路线。** 本仓库场景是"相似技能多、需要精确路由"（skill-create/skill-revise/spec-skill 三者高度相关），清晰的排除条件（Do NOT use when...）比单纯罗列触发词更能降低误选概率——这是场景特化的选择，不是放之四海皆准的正确答案，其他仓库场景不同可以有不同选择。

6. **三分设计（skill-create 新建 / skill-revise 修订 / skill-test 裁决）按生命周期边界划分，不按能力重叠划分，不做合一。** 边界是"新建 vs 修改"这条清晰的生命周期线：create 管从零、revise 管改动+测试门、test 是被两者复用的无状态裁决引擎。若未来要重新评估三分是否合理，判据应是"生命周期边界是否变得模糊"，而不是"技能数量看起来多"。

7. **子类规范（如 spec-task-skill）必须能被消费者感知到，不能靠人工记得加载。** 发现过 `skill-create`/`skill-revise` 处理 task 系列目标技能时，正文里完全没有判断分支去加载 `spec-task-skill` 的增量约定，全靠操作者记性。修法是在消费者的对应阶段加最小侵入的条件注入分支（按目标名/Dependencies 匹配），不是让消费者复述子类规范的规则内容——复述必然漂移，这条道理本仓库的 Self-Evolution 设计里已经讲透。

8. **中性判定不能只靠"人工重设计更隐蔽的 criteria"这一种缓解手段，需要客观的区分度检验补充。** 对比实验的"中性"退回此前完全依赖出题人事后猜测 criteria 是否泄漏答案。引入 Anthropic 官方 skill-creator 的"assertion 恒过/恒不过说明无区分度"分析陷阱识别法：先跑一次不注入任何技能文本的基线臂，若基线臂也 pass，问题在题目设计阶段就能被拦下，不必等两臂都跑完才怀疑。

## 已知例外登记

**skill-revise 不开自进化（无 lessons.md），经用户确认的设计例外。** 两段式范式要求"运行段只沉 lessons、固化走测试门"，但 skill-revise 自己的运行经验若沉 lessons 再固化，固化端就是它自己——自己给自己出题测自己的改动，测试门失去独立性（同一自指问题也体现在协议文件的"自指改造例外"节：改 skill-revise 自身时把关 = 改造前的现有流程，不用改后的工具自证）。代价是明确的：skill-revise 正文的改动缺实证门，只能靠合规订正路径 + changelog 人工把关。这是权衡后的已知例外，不是遗漏；若未来 skill-test 建立了独立于 skill-revise 的 Acceptance 体系，可重新评估。

## 与外部实践的取舍记录

调研 Anthropic 官方 best-practices、obra/superpowers、LangChain 团队实测基准后，三处交叉印证、可信度最高的结论已经体现在上述原则里（精简优于全面有实测天花板、解释原因优于生硬规则、skill 数量/相似度本身是误触发的独立变量）。两处存在分歧、本仓库明确选边而非各打五十大板：

- **薄 vs 厚整体哲学**：Anthropic 官方总体偏"信任模型、少写字"；superpowers 偏"重流程护栏、Iron Law 式强制测试"。本仓库选择更接近 superpowers 一端（多阶段流程 + 强制测试门），但坚持"每条规则必须有 Reason、允许模型泛化"的陈述式写法（原则 2），不做无解释的硬性堆砌。
- **是否需要专门的"元技能"**：官方原文明确表态"你不需要专门的 writing-skills 技能来帮你建 skill，Claude 天然理解 SKILL.md 格式"，倾向轻量对话式协作。本仓库仍保留 5 个专职元技能，理由是这套体系承担的不只是"写一个 skill"，还包括跨技能一致性维护、lessons 固化的测试门禁、多技能协同的编排族审查——这些是官方轻量建议未覆盖的治理需求，不是对官方建议的否定。
