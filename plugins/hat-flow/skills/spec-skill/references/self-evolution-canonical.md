## 自进化过程准则（受管 · 全局注入）

> 本区块由 `spec-skill` 统一维护、各自进化技能启动时直接注入其绝对路径，**自进化流程不得改它**。完整规范见 spec-skill 的 `## Self-Evolution Capability`。

**两段式自进化（核心范式）= 提议与固化分离**：

| 段 | 谁执行 | 允许动什么 | 不允许动什么 |
|---|---|---|---|
| **运行段**（自动 · 无人在环）：每轮运行 + 收尾复盘 | 任意 self-evolving 技能自身 / dogfooding | **只写 `~/.claude/.friction/` 临时文件 + `lessons.md`** | SKILL 正文 / reference / CLAUDE.md（一律不在运行段当场改） |
| **固化段**（人工把关 + 对比实验） | **仅 `skill-revise`** | 扫 `lessons.md` → 逐条判定 → 对比实验（skill-test 改前/改后两臂）通过的才升级进正文 / reference / CLAUDE.md，并从 lessons 移除 | — |

<rule>
运行段（每轮运行、收尾 dogfooding、自动复盘）对自身改进只允许写入 `~/.claude/.friction/` 临时文件与本技能 `lessons.md`；修改 SKILL 正文 / reference / CLAUDE.md 一律延后到固化段，由 `skill-revise` 在对比实验（skill-test）通过后执行。
Reason: 自生成的流程改动默认会退化（SkillsBench 实测自生成 skill 平均 −1.3pp、无确定性验证即累积 skill debt）。把「反思沉淀」与「采纳固化」分离、给固化加测试门，是防退化的保守闭环；运行段直接改正文等同无验证自改，正是要堵死的入口。
</rule>

> **lessons.md 两种形态**：流程类技能是**常驻 library**（自注入、冷归档、整合、硬上限）；spec 类（`spec-*`）技能是 **transient inbox**（仅作运行段候选收件箱，skill-revise 固化进正文后清空、不归档不整合、不自注入，读者是 skill-revise）。运行段写入动作相同，区别只在固化后是否清空。

**dogfooding 收什么**——每轮收尾要复盘的「摩擦点」有三类，**都在自进化范围内**，别只盯第一类：
1. **技能与实际不符**：流程缺步 / 顺序错 / 停点不对 / reference 不贴合 / 标准模糊。
2. **执行返工**：技能与脚本本身没错，但我**凭记忆猜了字段名 / 参数 / 文件名 / 数据形状**、先写命令再报错回改，绕了弯路。← 过去常被漏掉，于是同一类低级错误反复犯。这类也必须沉淀。
3. **规范失真（负向信号）**：技能文本与现实不符——照文本执行即失败（幽灵命令 / 漂移参数 / 不存在的引用）、声明的调用链已断裂、或某段规范本轮被合理跳过且无任何后果（疑似死文本）。← 自进化若只收前两类，正文只会单调增长；失真段落靠它们永远清不掉（2026-07-07 舰队审计实证：幽灵 `verify` 子命令、过时 permission_mode 枚举、断裂调用方声明，全都只能靠一次性人工审计发现）。

**摩擦点忠实记录（硬约束 · 自动默认 · 不通知用户）**：一旦检测到上述任一类摩擦点，**当场立即**追加一条到临时文件——不等收尾、不靠回忆、不打断用户：

- **位置**：`~/.claude/.friction/`（全局专用目录；**绝不写进任何项目树**，防污染与误提交）。
- **命名**：`<session-id>.md`（一会话一文件、**append 多条**，每条自带 UTC 时间戳；session-id 取 `$CLAUDE_CODE_SESSION_ID`，压缩 / 重开后仍按 session 精确关联）。
- **内容**：每条 = 时间戳 + 类别（①技能与实际不符 / ②执行返工）+ 涉及的技能名 + 一句摩擦描述 + 现场证据（命令 / 字段 / 路径）。
- **辅助**：`hat-friction-record --category 1|2 --skill <name> --desc "..." [--evidence "..."]` 提供标准写法（零依赖，session-id 缺省取环境变量）；无脚本时直接 append 一行同构 markdown。
- **静默**：写时不 AskUserQuestion、不在正文向用户报告，自动默认进行。

<rule>
检测到任一类摩擦点时，当场立即把它追加进 `~/.claude/.friction/<session-id>.md`（推荐用 `hat-friction-record`），静默、自动、不通知用户、不写进项目树。
Reason: 摩擦点若只在收尾凭记忆补，会被 compaction / 重开抹掉——这正是反复犯同类低级错的根因。即时落盘到会话隔离的临时文件，使收尾自进化读到忠实、完整的原始信号，而非残缺回忆。
</rule>

**先验后做（pre-flight · 根治第 2 类）**：对**任何形状不确定**的东西（API / JSON 字段、CLI 参数、文件名、目录结构、产物 schema）动手前，**先花一步确认真实形状**——`--help` / `ls` / 读一条样本 / 查文档——**再操作**，不凭印象直接写命令等报错。一次确认的成本 ≪ 一次错跑 + 回改 + 多花的 token。**尤其**：脚本静默产出空结果（空白图 / 空表 / 0 行）而不报错时，第一反应是回去核对字段 / 路径对不对，而不是接着往下跑。**文档与脚本同时落地时**：先敲定脚本的最简产物形状（文件名 / 结构 / 字段），再据此写规范文档；反序（先在规范固化 schema、后写实现）会致两者形状不一致、返工同步多处文档。

**收尾兜底（harness Stop hook，不靠自觉）**：收尾蒸馏依赖流程走完，会话中断 / 用户忘记发起时摩擦点会积压。`settings.json` 注册的 Stop hook（`bin/hat-friction-remind`）在本会话摩擦点 ≥3 时提醒用户可跑 `/dogfooding`（一会话只提醒一次、顺带报历史遗留文件数）——收到该提醒时如实向用户转达并询问，用户拒绝则接受、不再重复。**历史遗留**（其他会话积压的 `.friction/*.md`）的消化路径归 `/dogfooding`（读取→蒸馏进对应技能 lessons→移 `archive/`），收尾时发现遗留可顺带提一句。

**收尾沉淀（裁决漏斗 · 只分类打标、不固化）**——收尾时汇总本轮 `~/.claude/.friction/` 临时文件 + 本轮摩擦点，每条按序找**最高**出口，**命中哪层就给它打哪层的「建议出口」标记**，但本段**只把条目写进 `lessons.md`**、不当场改任何流程文件：

1. 流程问题（缺步 / 顺序错 / 停点不对 / 该调没调）→ 标记 `建议出口=正文`
2. 某 reference 不贴合 / 可优化；**或某次返工暴露了一份可文档化的形状**（字段名 / 参数 / 路径速查）→ 标记 `建议出口=reference`
3. 通用判断规则（适用多数场景）→ 标记 `建议出口=CLAUDE.md`
4. 稀有 / 例外经验（前三层都小题大做）→ 标记 `建议出口=lessons`（就地留存）

**①②③④ 全部条目一律先进 `lessons.md`**（带「建议出口」标记），固化由 `skill-revise` 在固化段按该标记分流执行——运行段不再当场上移。

**负向候选（删 / 改，对应第 3 类摩擦）**：建议出口标 `正文订正`（文本错了，附现实证据：实测输出 / 现行 schema / grep 结果）或 `正文删除`（文本疑似不承重，附「被跳过且无后果」的现场）。与加法候选同走两段式——运行段只沉 lessons 不动正文；固化端由 `skill-revise` 按**负向模式裁决**（见其对比实验协议：删除候选的「两臂等效」= 该段不承重 = 支持删除，与加法候选的中性语义相反）。有实测证据的**事实性订正**（幽灵命令 / 参数漂移这类照做必失败的）可走合规订正路径直改，无需对比实验——证据即裁决。

> **第 2 类返工的归途**：① **能文档化的形状**（如 `meta.json` 落盘字段、session JSON 用 `lines` 非 `rows`）记一条标 `建议出口=reference`；② **纯纪律性疏忽**（信息本可 `--help`/`ls` 当场拿到、只是没做）由「先验后做」覆盖，**不建经验库条目**；但**若反复在同一处栽**，记一条标 `建议出口=正文`（建议某 Phase 开头加一个针对性 pre-flight 检查点）。
> **编排族补一问**：「下次哪个技能的哪个决策点会读到它？」——执行细节归 worker、编排决策归 orchestrator；答不出唯一归属就别写（**绝不把同一软经验镜像进多个技能**）。

**写入闸（反转 · 运行段默认进 lessons）**：运行段把经验写进 `lessons.md` 是默认动作，**无需论证「为何不上移」**——上移（固化）已转交 `skill-revise` 且需对比实验（skill-test）。运行段唯一要把关的是：**这条是否真是可复用经验**（而非一次性纯纪律疏忽——那类由「先验后做」覆盖、不建条目）。够格 → 写一条带「建议出口」标记；不够格 → 丢弃。

**沉淀带上下文 + 出处（供异步固化理解）**：每条经验在「来源」列填两样——① 一句**简短上下文**（这条经验产生的情境 / 为何重要，让日后固化时无需回放全程即可理解）；② **原始出处指针**（指向可回溯的源：commit 短 hash / `.tasks` 归档文件夹名 / PR 号等，可内联或用 markdown 角标 `[^x]`；确无出处可留空）。Reason：沉淀与固化**异步**——固化方若只见一句干经验、缺情境，常判不出该「改写描述以固化」还是「抛弃」；带上下文 + 出处，`skill-revise` 才能据情境（必要时回溯原始出处）决定固化措辞或给出抛弃建议。**固化采纳后，这些上下文 + 出处一并剥离、不进正文**——它们是给固化决策用的脚手架；正文只留对当前技能的正面陈述，溯源信息归 changelog。

**整合（触发式，非每轮强做）= 淘汰 + 归纳覆写**（**升级固化已转交 `skill-revise` 固化段**）：超限 / 过时的**淘汰**进 `lessons-archive.md`（不删、可回溯、永不注入、高重要度豁免）；**归纳覆写**合并重叠、刷新「上次命中」。经验库表格化（`经验|重要度|建议出口|来源|上次命中`）、头部记 `上次整合: YYYY-MM-DD`、**硬上限 ≤15 条**。触发判据只看两样：达硬上限 / 距上次整合 ≥1 天（或到上线·里程碑节点）→ 做；本轮无新经验 / 刚整合过 → 跳过。整合后刷新头部日期。

**changelog 纪律**：`references/changelog.md` **仅在固化段真正改了 skill 定义**（SKILL.md / reference / 经验库结构）时写一条，记「改了什么 + 为何」，最新在最上。**运行段只写 lessons / friction 临时文件、不改 skill 定义，故运行段不写 changelog**——它是修订 / 回溯日志，不是每轮运行或 dogfood 的流水账。
